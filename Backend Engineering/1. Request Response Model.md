#### Overview
We can break the Request Response Model down into these steps:
* Client sends a request.
* Server parses the request.
* Server processes the request.
* Server sends a response.
* Client parses the response and consumes it.

This model is used all over the web. 
* HTTP, DNS, SSH and RPC.
* SQL and database protocols.
* APIs, including REST, SOAP and GraphQL.

#### Anatomy
For a request-response model, a request model is defined by both the client and server, so that both systems can understand the concept of a request. For HTTP, libraries often abstract this away from the programmer. The request has a boundary, and is defined by a protocol and message format.

#### Pitfalls
There are some use cases where a request response model is not ideal. A notification service, for example, is not great here, as we would have to continually poll for notifications. This does not scale well. The same example can apply to chat applications, for example.

Request response is also not suitable for use cases that would require long requests. We could use asynchronous requests to help mitigate this.

#### Costs
As with many backend models, there are costs that apply to each stage of the request/response model. There are costs involved in, for example:
* Creation of the request by the client.
* Network transfer time.
* Time taken to arrange packets received by the server.
* Time taken to parse the request.
* Time taken to process the request.
* Time taken to create the response and send it back to the client.

#### Anatomy of a HTTP request
We can view a HTTP request and its response using `curl` with the `--trace` option. You will see a range of bytes which translate to the human-readable strings that form a HTTP request.

Requests start with their method, then the resource to be requested, then the HTTP protocol version number. They are followed by headers, then followed by the request body, e.g.:

```http
POST /cgi-bin/process.cgi HTTP/1.1
User-Agent: Mozilla/4.0 (compatible; MSIE5.01; Windows NT)
Host: www.tutorialspoint.com
Content-Type: text/xml; charset=utf-8
Content-Length: **length**
Accept-Language: en-us
Accept-Encoding: gzip, deflate
Connection: Keep-Alive

<?xml version="1.0" encoding="utf-8"?>
<string xmlns="http://clearforest.com/">string</string>
```

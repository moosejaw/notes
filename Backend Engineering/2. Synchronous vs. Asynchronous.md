Sync vs. Async boils down to "can I do other work while waiting?"

To make something asynchronous means that the client and the server are not in sync with each other. Asynchronous execution is usually preferred to synchronous execution.

#### Synchronous IO
In synchronous IO, the caller will send a request and block. This means that **nothing else can happen (related to this task) whilst the block is in place.**

When the CPU recognises that synchronous IO is happening, it context switches to another task, as it knows that it cannot proceed with the current task due to the block.

When the receiver responds, the caller will unblock. Effectively, the caller and receiver are "in sync."

##### Example of an OS-level synchronous IO
* Program asks OS to read from disk.
* Program main thread is taken off the CPU (CPU context switches to another process)
* The read completes, and the program can resume execution.


#### Asynchronous IO
In asynchronous IO, the caller will send a request, and the caller can work until it gets a response. The question here is, **how does the caller know when the response is ready?**

Some solutions include the caller checking to see if the response is ready (`epoll` syscall in Linux), or having the receiver call back when it is done (such as `io_uring` in Linux). When these are unavailable, some applications will occasionally start a new thread to perform the blocking operation, so that the main thread is free to carry on.

This means the caller and receiver are not necessarily in sync.

##### Example of OS asynchronous IO
* Program starts a secondary thread.
* Secondary thread reads from disk, OS blocks it.
* Main program is still running and executing code.


> [!INFO]
> The above paragraph explains to us how async is not always necessarily the same as multithreading or multiprocessing. 
> 
> While all achieve concurrency, asynchronous IO can still happen within the main thread, thanks to our system calls such as `epoll` or `io_uring` on Linux. We can process blocks of work and keep polling the outstanding events to check they are completed.


#### Tying it back to Request Response
The vast majority of modern request response libraries are asynchronous. We know that we are sending lots of network requests, and we'll want to do other work in the background whilst awaiting the response.

#### Applications of async
The uses cases of asynchronous workloads are vast. Asynchronous programming (using promises/futures/coroutines) is very common. 

Asynchronous backend processing is another. A client request will get put into a queue in the backend, and the backend will return some kind of handle or promise that a response will be returned. This handle will contain a job ID or something similar so that the client can continue to access the request.

Other examples include:
* Asynchronous commits (in Postgres)
* Asynchronous IO in Linux
* Asynchronous replication
* Asynchronous OS fsync (flushing the OS cache to the disk)
